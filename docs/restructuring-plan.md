## 初版交付范围

长期按 [产品需求](product-requirements.md) 恢复完整旧项目。初版先接通底栏的主城、英雄、背包、战斗、副本、公会、VIP，以及商店、抽卡等主城基础入口。下表是每个模块的建议验收范围。更多主城入口按旧版解锁顺序、主循环依赖及玩家操作逐个定范围。

| 模块 | 初版建议 |
|---|---|
| 主城 | 按原开放条件显示入口，地图特效与入口分层，入口可点且返回路径正确 |
| 英雄 | 名册、详情与技能可读，真实首抽获得英雄，布阵和基础升级、穿脱可操作。按旧引导确认碎片合成和进阶进入主循环的时点 |
| 背包 | 四类物品详情及到账状态可查，接通成长实际依赖的使用、合成与穿脱入口 |
| 战斗 | 主线连续已验关卡、阵容编辑与保存、真实结算、战报和挂机领取，断线后恢复原结果 |
| 副本 | 底栏已恢复旧版 `SlzmLayer` 副本大厅和奖励预览，日常副本已接通金币首关的挑战、扫荡、次数、结算与奖励 |
| 公会 | 走通公会查找、创建、申请、审批和退出。用两个角色检查管理权限、成员同步和重连 |
| VIP | 先核对第七个按钮实际进入的旧 VIP 任务页，从等级进度、任务、权益和对应领奖做一条闭环。实际充值随渠道支付方案安排 |

每个初版入口验收实际可进行的业务和原解锁条件。普通新号可从主城取得英雄、布阵、完成首战并继续成长。旧配置中副本大厅和公会分别在角色 15、18 级开放，验收时要确认已有主线与收益能进入对应等级。若自然成长不足，按原规则补经验来源或已接通的关卡。涉及消耗或发奖的操作检查重复请求、失败回滚与重登，副本和主线复用战斗、通用发奖与恢复链。

## 主城与布阵怎么实现

主城入口已在 `CityHubView` 的 `BuildingEntries` 层绘制，滚动时仍按原视差层换算。布阵手势、保存和草稿维护入口见 [阵容页面](formation-ui-authoring.md)。

| 优化 | 实现与验收 |
|---|---|
| 点击英雄自动入位 | 旧 `HeroSelectCtr.lua` 按当前阵型开放位置的编号升序找首个空位。基础阵型的普通格为 2、3、5、6、7、8，首先填 2 号。助战位按独立解锁规则处理。点击已上阵的英雄移除，同模板重复入队给出提示。按现有 `MainFormation.options` 的允许位置编辑草稿 |
| 拖动已上阵英雄 | 拖到开放空位则移动，拖到合法占用位则交换，未命中或目标不可用时回原位。拖拽只改 `FormationView` 草稿，确认时使用现有 `formation.save` 和统一快照。验证取消触摸、关页、前后排移动、锁位和回弹 |
| 列表上阵标记 | 用草稿中的英雄实例 ID 驱动 `FormationHeroCellView` 内的局部暗层和现有绿色勾。暗层保留原格子的点击，列表复用时每次完整更新标记 |
| 阵型选择 | 已通过本机预览。契约阵型窗读取同源 `battlematrix`、`battlematrixaddition` 显示门槛、普通开放格与格位属性。确认修改草稿，英雄按新旧开放格的相对顺序迁移，出阵后保存 |
| 元素抑制 | 已通过本机预览。`heroelemmul` 显示对敌相克、命中与伤害。`elementaddition` 显示同元素及五元素混合档位，当前激活组置顶，每组只高亮一个实际生效档 |
| 站位与队伍加成 | 契约阵型窗展示格位加成，出阵页和元素抑制窗显示草稿的光环合计。应用倍率仍由主线服务端的 `HeroBattleInputService` 与 `HeroBattleChapterScenario` 按原流程计算。完整战力显示随英雄属性恢复核对旧聚合口径 |

助战参战仍有独立规则缺口，待能力接通后再开放对应交互。英雄详情按完整属性与技能来源继续恢复。首战奖励足以完成旧引导9级门槛，穿装排在命名、赠礼和普通召唤之后。[阵型与保存](hero-lineup-contract.md#2026-11-04-主线阵容最小保存闭环)

## 主线第 41～550 关

第 1～550 关已连续开放。第 41～100 关补齐守军所需英雄技能、旧动作和奖励依赖，Creator 核对第 50、80 关里程碑及第 100 关实战、结算与独立通关奖励。第 101～110 关用达到第 110 关准入等级 33 的角色连续实战，Creator 抽验第 101、103、110 关，第 103 关验证开膛手·J 的替换普攻，第 110 关验证两种领取。

第 111～300 关通过独立测试服连续实战。第 159 关开始遇到前批未接入的入场被动，第 201 关开始使用二级被动和替换普攻。第 200→201 关沿原表从 `map08` 切到 `map10`，第 300 关沿用 97 级门槛和 `map11`。Creator 抽验第 140、201、281、300 关实战与结算，以及第 206、283、300 关的周期伤害、反击与攻击表现。

第 301～360 关补齐五项三级被动，动作和地图复用原资源。第 301、351 关分别切换到 `map17`、`map20`，第 330 关起沿用挂机掉落组 `1015`。第 360 关保留 117 级门槛，Creator 实领两件独立通关奖励。

第 361～400 关补齐七项三级被动和一项三级主动，恢复五个三级动作的原表现分支。全段沿用 `map20` 与挂机掉落组 `1015`。第 400 关保留 131 级门槛，实领 50 碎片和 50 钻石。

第 401～440 关补齐八项三级技能，恢复凯萨丁三级替换普攻的两段旧特效。第 401 关结算后从 `map20` 切到 `map23`。第 440 关保留 143 级门槛，独立通关奖励为两件装备。

第 441～550 关沿用现有技能和掉落组 `1015`。第 451 关结算后从 `map23` 切到 `map25`。第 550 关保留 201 级门槛，独立通关奖励为 50 碎片和 50 钻石。

后续提高挑战上限前，用独立测试服验证连续挑战、结算、挂机和发奖，用 Creator 本机抽验新增技能、地图切换和关键领奖。角色等级和战力门槛按原配置执行。[进度与验证](development-progress.md#当前验证与边界)

## 下一批的新号流程

1. **命名已接通。** 首次进入主城时按 `Role.firstNamed` 开窗，支持随机或手动输入，成功以服务端快照更新顶栏。刷新先回登录页，点「开始游戏」后继续角色进度。加权长度按策划表的 25 校验。
2. **新手赠礼已接通。** 首次命名后按 `Role.welcomeGiftAvailable` 打开领取窗。按 `guide_initial_reward` 一次性发放，共 492 钻及三种物品，到账经过通用发奖流程。普通召唤券来自创角邮件 `create_role_mail_reward_one`，Lua 和策划表的数量有差异，等接入邮件时核对。
3. **召唤页面已接通。** 主城法阵打开独立内容页，使用日服的三张召唤卡、看板和背景。三池支持单抽与十连，积分兑换按实际资格开放，祈愿显示解锁条件。客户端显示实际抽取结果，首抽和保底由服务端处理。

顺序依据为日服本地 `客户端/lua-src/config/guide/guideentire.lua`，赠礼和首抽配置位于 `客户端/web-jpn/jp-overlay/src/config/system.lua`。画面以负责人 11 月 19 日提供的新号截图为准。

主城后续接入带开服天数门槛的建筑时，需把服务器认定的区服天数传给地图。现有地图把 `openDay` 固定传为 0，例如魔塔的 `magic_tower_open_day` 会一直按第 0 天判断。项目已有的角色创角时间只适用于角色自己的挂机计时。

## 首战之后怎么推进

日服新号的顺序是第一段剧情、剧情战斗、第二段剧情、进入主城、命名、领取新手赠礼、打开召唤法阵、普通单抽，然后布阵。剧情战斗发生在进入主城前，与布阵后的主线第 1 关分别验收。当前代码保留了首笔单抽、真实发奖和首战结算。剧情、剧情战斗和引导手势留到后续。[当前进度](development-progress.md#当前验证与边界)

1. **普通装备已接通。** 旧引导在布兰特达到9级后引导一键穿装。英雄详情的空槽选择、已穿查看、手动换装与一键择优均已接到服务端，后续引导复用现有按钮与协议。
2. **普通市场已接通。** 使用旧 `shopmarket`、`shopcontrol` 和 VIP 刷新次数配置。新号可用赠礼钻石购买有余额的真实商品。服务端保存货架、限购与刷新的实际结果，回城或跨日重登仍读到原货架。[普通市场通信](network-contract.md#普通市场)

## 主线剩余缺口

- 灵器、天赋、精灵、觉醒等参战输入，以及助战、先手、部分技能与控制表现仍有缺口。规则与画面按 [战斗问题表](battle-known-issues.md) 分别跟踪。
- 状态中还有待结算的战斗编号时，重进主线可以继续结算。已结算且只缺奖励表现时，重登以到账数据为准。
- 通关后需要接入的任务或活动效果随所属功能恢复。后续里程碑随着连续关卡开放，再逐一验证资格、回执和对应奖励画面。

## 日常副本首关

旧 `MainSceneCtr.lua` 用 `main_mission_hall` 显示底栏 15 级门槛，开页还核对 `main_mission`。大厅四张卡按角色等级 15、25、30、35 顺序解锁，`gamerewardshow` 提供产物图标。各玩法接入时再开放对应入口。

金币首关的缇芮一级主动与主线第 22 关复用 `2041401`。大厅从日常副本卡进入此关，服务端用历史最高主阵容战力严格大于门槛判断，界面展示同一权威状态。首胜后可扫荡，跨日保留首通资格。后续开放更多关卡时逐关核对真实敌方技能、资源、奖励和每日规则。[通信契约](network-contract.md#金币副本首关)

## 挂机剩余缺口

- 快速战斗、活动角色进度、兑换、到期回收及额外成长各自恢复资格、次数、价格、时间或发奖规则，复用已有资产事务。
- 新环境须提供真实开服日期与活动控制。044发布还需当前版本、期限和兑换配置，操作见 [活动控制](idle-activity-maintenance.md)。
- 目标 MySQL 复用独立验证入口，先覆盖现有主线、挂机和里程碑的锁、回滚与重放，首抽接通后补同一角色并发的检查。目标平台拿到资源地址后，验证三段加载、换号、持久存储、异常退出及真实前后台。[独立环境](local-remake-workflow.md#独立-mysql2026-11-02) · [资源加载](staged-resource-loading.md)

| 随战斗调整 | BattleReplayPreview 先将位置参数改为具名场景选项，再收敛技能台和播放器的动作预检。正式、挂机和开发演示的开场及取消归属分别验证 | 表现预检、战场资源失败、结算归属和关页或换号清理 |
| 有明确迁移时 | 旧 CampaignService 和 IdleService 仍被领域与 MySQL 测试使用。先迁移测试数据准备和重放断言，再退役旧服务 | 迁移前后覆盖相同并发、回滚与资产版本边界 |

保持主线结算、挂机领取、里程碑领取各自的幂等标识和恢复机制。共享发奖负责可信分发，状态通知同步资产，奖励通知驱动展示。三者边界见 [架构](architecture.md#共享可信发奖)。

## 每批工作的完成条件

1. 明确范围，核对已有配置、调用链和资源依赖。
2. 先复用已有领域、通信和页面能力。涉及素材、节点及脚本迁移时核对 UUID 和绑定。
3. 用独立后端和 Creator 本机预览验证玩法。上线前按目标环境验证发布包与真机。将每种结果记录在对应的验收证据中。
4. 更新负责该事实的主文档。旧计划可查 [历史快照](validation/restructuring-plan-history-20261113.md)。
