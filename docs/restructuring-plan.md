# 实施路线

更新于 2026-11-18。[当前进度](development-progress.md) 维护已实现范围与验证证据。本页只记剩余工作、依赖和决定。

## 初版交付范围

长期按 [产品需求](product-requirements.md) 恢复完整旧项目。初版先接通底栏的主城、英雄、背包、战斗、副本、公会、VIP，以及商店、抽卡等主城基础入口。下表是每个模块的建议验收范围。更多主城入口按旧版解锁顺序、主循环依赖及玩家操作逐个定范围。

| 模块 | 初版建议 |
|---|---|
| 主城 | 按原开放条件显示入口，地图特效与入口分层，入口可点且返回路径正确 |
| 英雄 | 名册、详情与技能可读，真实首抽获得英雄，布阵和基础升级、穿脱可操作。按旧引导确认碎片合成和进阶进入主循环的时点 |
| 背包 | 四类物品详情及到账状态可查，接通成长实际依赖的使用、合成与穿脱入口 |
| 战斗 | 主线连续已验关卡、阵容编辑与保存、真实结算、战报和挂机领取，断线后恢复原结果 |
| 副本 | 底栏先恢复旧版 `SlzmLayer` 副本大厅，优先考察其中的每日副本。走通解锁、准入、次数、战斗、结算与奖励 |
| 公会 | 走通公会查找、创建、申请、审批和退出。用两个角色检查管理权限、成员同步和重连 |
| VIP | 先核对第七个按钮实际进入的旧 VIP 任务页，从等级进度、任务、权益和对应领奖做一条闭环。实际充值随渠道支付方案安排 |
| 主城基础入口 | 抽卡先接普通首抽，再按原配置补初版所需的单抽规则。商店先复用旧主城默认的普通市场，验证买入真实配置商品、扣费、限购、到账与重登 |

每个初版入口验收实际可进行的业务和原解锁条件。普通新号可从主城取得英雄、布阵、完成首战并继续成长。旧配置中副本大厅和公会分别在角色 15、18 级开放，验收时要确认已有主线与收益能进入对应等级。若自然成长不足，按原规则补经验来源或已接通的关卡。涉及消耗或发奖的操作检查重复请求、失败回滚与重登，副本和主线复用战斗、通用发奖与恢复链。

## 主城与布阵怎么实现

主城入口已在 `CityHubView` 的 `BuildingEntries` 层绘制，滚动时仍按原视差层换算。布阵手势、保存和草稿维护入口见 [阵容页面](formation-ui-authoring.md)。

| 优化 | 实现与验收 |
|---|---|
| 点击英雄自动入位 | 旧 `HeroSelectCtr.lua` 按当前阵型开放位置的编号升序找首个空位。基础阵型的普通格为 2、3、5、6、7、8，首先填 2 号。助战位按独立解锁规则处理。点击已上阵的英雄移除，同模板重复入队给出提示。按现有 `MainFormation.options` 的允许位置编辑草稿 |
| 拖动已上阵英雄 | 拖到开放空位则移动，拖到合法占用位则交换，未命中或目标不可用时回原位。拖拽只改 `FormationView` 草稿，确认时使用现有 `formation.save` 和统一快照。验证取消触摸、关页、前后排移动、锁位和回弹 |
| 列表上阵标记 | 用草稿中的英雄实例 ID 驱动 `FormationHeroCellView` 内的局部暗层和现有绿色勾。暗层保留原格子的点击，列表复用时每次完整更新标记 |
| 阵型选择 | 已通过本机预览。契约阵型窗读取同源 `battlematrix`、`battlematrixaddition` 显示门槛、普通开放格与格位属性。确认修改草稿，英雄按新旧开放格的相对顺序迁移，出阵后保存 |
| 元素抑制 | 已通过本机预览。`heroelemmul` 显示对敌相克、命中与伤害。`elementaddition` 显示同元素及五元素混合档位，当前激活组置顶，每组只高亮一个实际生效档 |
| 站位与队伍加成 | 契约阵型窗展示格位加成，出阵页和元素抑制窗显示草稿的光环合计。应用倍率仍由主线服务端的 `HeroBattleInputService` 与 `HeroBattleChapterScenario` 按原流程计算。完整战力显示随英雄属性恢复核对旧聚合口径 |

助战参战仍有独立规则缺口，待能力接通后再开放对应交互。英雄详情按完整属性与技能来源继续恢复。首战奖励足以完成旧引导9级门槛，接下来恢复穿装。[阵型与保存](hero-lineup-contract.md#2026-11-04-主线阵容最小保存闭环)

## 第21～25关怎么实现

第21关及第23～25关已通过静态依赖检查。第22关的缇芮一级技能 `102040041:1` 有动作 `2041401`（`type=10`），服务端场景预检与客户端动作计划都拦截。第26关还有未核对的帧资源声明，作为后续批次入口。[当前依赖报告](validation/main-chapter-dependencies-20261117-stage20.txt)

1. **先跑通第21关。** 在独立环境用第20关进度与现有阵容保存入口准备测试角色，通过现有主线协议挑战第21关，检查地图、敌方技能、战报、首通回执及挂机收益更新。运行期间用 `MXZG_MAIN_CHAPTER_CHALLENGE_LIMIT` 设置独立环境的上限，默认上限在验收完成前保留20。扩关沿用服务端下发的上限和原页面入口，可复用 `MainChapterConfigurationTest` 的连续挑战用例。
2. **补齐第22关的两段技能表现。** 旧 `battle/actions.lua` 给 `2041401` 定义了两段覆盖。先用 `type=6` 播原地暗屏、帧动画和音效，再用 `type=10` 从角色向战场固定比例坐标投掷，飞行时长按帧数乘每帧时长。复用已有帧图和音效，在 `BattleAttackUtils` 补齐动作计划，由 `BattleReplayPreview` 播放。服务端通过 `HeroSkillPanelRules` 接入表现动作校验，沿用原技能结算。用真实 Protobuf 战报检查两段顺序、飞行位置、变速、关闭清理和技能台播放。
3. **连续验收并开放。** 重新导出 Java 能力与资源依赖报告，连续挑战并结算第21～25关，检查原战斗编号恢复、重复结算回执、真实首通入账、背包/角色快照及挂机档位。Creator 本机抽验第21关、缇芮出场的第22关与末关。通过后把默认值推进到已验证的连续关卡，并检查下一关仍会拒绝新挑战。若第22关还有经核对的缺口，先开放通过整套检查的第21关。

## 首战之后怎么推进

旧引导先命名、领一次性新手赠礼、普通首抽，再布阵挑战。免费首抽与首战已接通。命名、一次性赠礼和后续招募仍待恢复。首战后的独立通关奖励和精英碎片合成已有实际到账与冷重登记录。[当前进度](development-progress.md#当前验证与边界)

1. **普通装备。** 旧引导在布兰特达到9级后引导一键穿装。利用首战及通关奖励已经获得的装备验证槽位、择优与归属，检查穿脱后的参战属性、战报和重登状态。先核对旧单槽和一键处理各自的替换顺序。
2. **基础商店。** 核对普通市场入口、首次开放与实际商品来源，优先接一笔可由普通新号完成的真实购买，验证扣费、限购、发奖和重登。

## 主线剩余缺口

- 第26关补齐 `103040041:1` 的动作 `3041101`。按旧版两段覆盖衔接前移返回、目标特效及帧索引，优先复用现有素材。第27～29关沿用同一套实战验收。第30关再核对 `104040021:1` 的条件子动作与帧参数，沿用已通的里程碑回执链验证奖励 `900102 ×500`。第551～850关的关卡坐标存在源数据差异，等依据确认后再处理。[最新依赖报告](validation/main-chapter-dependencies-20261117-stage20.txt) · [里程碑](main-chapter-milestone.md)
- 灵器、天赋、精灵、觉醒等参战输入，以及助战、先手、部分技能与控制表现仍有缺口。规则与画面按 [战斗问题表](battle-known-issues.md) 分别跟踪。
- 已结算、服务器已清 pending 且本地遗失 battleId 时，重登无法定位尚未展示的反馈。如需补展示，先确定保留期限和完成语义，再复用原回执。资产到账与反馈恢复分开。
- 通关后需要接入的任务或活动效果随所属功能恢复。后续里程碑随着连续关卡开放，再逐一验证资格、回执和对应奖励画面。

## 挂机剩余缺口

- 快速战斗、活动角色进度、兑换、到期回收及额外成长各自恢复资格、次数、价格、时间或发奖规则，复用已有资产事务。
- 新环境须提供真实开服日期与活动控制。044发布还需当前版本、期限和兑换配置，操作见 [活动控制](idle-activity-maintenance.md)。
- 目标 MySQL 复用独立验证入口，先覆盖现有主线、挂机和里程碑的锁、回滚与重放，首抽接通后补同一角色并发的检查。目标平台拿到资源地址后，验证三段加载、换号、持久存储、异常退出及真实前后台。[独立环境](local-remake-workflow.md#独立-mysql2026-11-02) · [资源加载](staged-resource-loading.md)

## 代码维护顺序

| 优先级 | 现状与做法 | 验证重点 |
|---|---|---|
| 已处理 | 技能台列目录时扫描，单份下载只校验对应文件。战报名册、名称和步骤可在同次解析中取得 | 文件变化、坏战报、旧报文、正常开场和技能演示 |
| 低风险 | 主线、挂机、里程碑各自递归检查回执数值能否由客户端精确表示。适合提取共享校验，业务层保留各自错误文案及事务调用点 | 非法值拒绝、部分入账回滚、旧回执重放 |
| 随业务调整 | 快照与里程碑在角色锁内再走公开主线查询，存在重复锁定和鉴权。可先统一主线状态的版本更新，再收敛为带明确前置条件的事务内查询 | 期限回收引起的版本变化、跨角色隔离。里程碑状态查询在只读事务内取角色锁，目标 MySQL 需实测 |
| 随战斗调整 | BattleReplayPreview 先将位置参数改为具名场景选项，再收敛技能台和播放器的动作预检。正式、挂机和开发演示的开场及取消归属分别验证 | 表现预检、战场资源失败、结算归属和关页或换号清理 |
| 有明确迁移时 | 旧 CampaignService 和 IdleService 仍被领域与 MySQL 测试使用。先迁移测试数据准备和重放断言，再退役旧服务 | 迁移前后覆盖相同并发、回滚与资产版本边界 |

保持主线结算、挂机领取、里程碑领取各自的幂等标识和恢复机制。共享发奖负责可信分发，状态通知同步资产，奖励通知驱动展示。三者边界见 [架构](architecture.md#共享可信发奖)。

## 每批工作的完成条件

1. 明确范围，核对已有配置、调用链和资源依赖。
2. 先复用已有领域、通信和页面能力。涉及素材、节点及脚本迁移时核对 UUID 和绑定。
3. 用独立后端和 Creator 本机预览验证玩法。上线前按目标环境验证发布包与真机。将每种结果记录在对应的验收证据中。
4. 更新负责该事实的主文档。旧计划可查 [历史快照](validation/restructuring-plan-history-20261113.md)。
