更新：2026-11-16。本文只维护后续顺序、依赖和完成条件；已实现状态及证据见[当前进度](development-progress.md)。开发继续在 `hao`；本次推送及合并 `main` 已获负责人授权，后续提交/推送仍按各次指令。旧P0–P10流水见[历史路线](validation/restructuring-plan-history-20261113.md)，不按旧待办重复实施。

## 当前判断

统一配置包、三段加载、模块资源目录、资源池、页面/Prefab缓存、共享模态及等尺寸虚拟列表已经具备。通用奖励反馈、确认框、挂机持久恢复、主线结算双确认、冷重登首次主线恢复、布阵确认及叠窗生命周期也已接通，并有各自限定检查和本机证据。

接下来应从反复补恢复矩阵转向**已有功能的具体缺口**。不继续无目标全仓重命名、不新增Manager/第二份状态、不以“继续检查”为理由反复要求刷新或构建。当前仍是前三关可玩子集，完整旧游戏缺口以[产品要求](product-requirements.md)和[战斗问题表](battle-known-issues.md)为依据，不能用测试数估算总体完成率。

## 接下来的执行顺序

| 优先级 | 下一批范围 | 完成条件及边界 |
|---|---|---|
| 1：核对主线实际奖励与展示 | 对照旧源码确认普通胜利与冷恢复对升级赠钻、经验变化、额外奖励的展示规则；检查当前基础奖励回执遗漏 | 先记录已知信息来自哪里，必要时在原业务持久回执/协议中保留真实明细，再复用现有奖励反馈。不能以钱包差补猜、不能重算旧奖励、不能另造主线专用通用窗。正常/冷恢复各展示一次，历史缺字段明确处理 |
| 2：按上一批改动做限定预览 | 验证实际变更的胜利页/通用奖励窗、叠窗和关闭；顺带确认同步onOpen保护、战场/播放器结算归属已进入Creator | 不重复全套118/98秒断线矩阵；无新相关改动就不重跑历史流程。现有本机证据与本轮新证据分别记录，不集中构建 |
| 3：领取开放前依赖复核 | 在负责人决定开放领取前，核查真实区服开服时间/活动控制、目标平台持久存储和部署数据库；把剩余问题列成有限清单 | 当前客户端策略、玩家按钮、日常服务端新请求仍关闭。仅测试环境可显式开启；复核不代表已经授权上线或开放。已有纯计算、回执、发奖、满额确认和恢复链直接复用 |
| 4：下一项玩家功能 | 待上项具体范围确定后，按旧源码逐项恢复养成、更多关卡/技能或其他模块 | 每批明确规则、权威数据、协议、界面和验收边界；完整依赖先恢复后调用，不用单页假表现填缺口。升级/穿脱、快速战斗等仍需相应授权 |

第1项是建议的下一次开发任务，不由本次代码整理自动扩大为实现授权。先读 `MainChapterRewardService`、当前持久战报/结算协议和 `RewardGrantResult`：现有共享发奖已产生升级附赠，但主线只保留基础实际量与既有经验动画，这是可定位的差异。若旧源码与当前规则无法确认，记录问题并询问，不凭正式服一次钱包变化推断。

## 每批工作的完成条件

1. 先读当前进度、实际Git与涉及代码，确定一批有终点的范围；在hao开发，提交/推送/合main遵循当次授权。
2. 核实旧源码/配置，复用已经具备的数据和通用能力；资产由服务端权威事务处理，页面不收包或改资产。
3. 对确定问题做最小职责修正，同步中文说明；移动脚本/资源保留原meta与UUID。删除前同时查调用、动态路径、绑定、生成器与工具。
4. 运行与改动匹配的检查；源码、受控专项、本机画面、发布包和真机分别记录。纯文档更新只核对内容和链接。
5. 更新对应唯一维护文档；历史证据留在validation，不再在三个入口反复堆“本批”。已实现、已验证和已开放分别写。
