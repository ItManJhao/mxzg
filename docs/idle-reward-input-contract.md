# 挂机完整加成输入契约草案

日期：2026-11-09。本文是下一阶段可审阅的服务端设计，不是已实现接口或领取开放说明。本批不修改 `.proto`、数据库结构、角色状态或游戏入口。旧规则依据见[奖励审计](idle-reward-rules.md)，现有基础随机边界见[测试记录](validation/idle-rule-boundaries-20261109.json)。

## 已有事实与缺口

- `protocol/game.proto:MainChapterIdleState`只有服务器时钟、起点、最大时长、周期、奖励关卡、基础速率和挂机选人；`rates`不能改称完整收益。`IdleEncounter`只是演出战报，不能作为发奖凭证。
- `game_main_chapter_idle`只有角色键和起点；新主线尚无累计随机窗口、保底计数和领取回执。`game_idle/game_idle_receipt`属于旧简化链，不借用它们给新页面领取。
- `V10__hero_capacity.sql`已有`game_role.goddess_vip`，默认0；当前生产读取点为`HeroCapacityService`。这证明字段存在，不证明羁绊养成写入、恢复推送及挂机加成已经接通。不新增第二份VIP字段，也不以客户端倍速默认档反推VIP。
- 角色等级及主线通关状态已存在；神职、世界等级、活动记录期/轮次、礼包持有与期限尚无主线奖励输入链。活动概率缺字段、世界等级旧接线及礼包到期秒仍待确认。

## 输入由谁提供

以下是拟定的业务字段，不是新协议字段名或字段号。完整计算在服务器执行，客户端不提交加成、时间、计数或奖励数量。

| 输入 | 内容、单位与来源 | 冻结与校验 |
|---|---|---|
| 领取上下文 | 当前认证角色、区服、请求标识及请求内容指纹 | 使用服务器会话归属；回执按角色和请求标识唯一，同标识不同内容拒绝 |
| 计算时刻 | 服务端Unix秒；持久挂机起点 | 在事务计算入口捕获；不接受客户端时间。到期等号按确认后的规则处理，不能由多个页面时钟决定 |
| 主线状态 | 已通关关卡及本次所用配置版本 | 角色锁内读取；不能用说明页当前选中关卡。保持当前前三关开放范围 |
| 挂机累计状态 | 上次领取后的累计秒数、按item_group_type保存的原始掉落数量/未中次数、持久操作版本 | 与新主线起点同一所有者；操作版本不同于全资产revision，不以连接ID代替 |
| 基础配置 | 周期、初始时长、基础最大时长、重置周期、基础奖励及随机组/触发器/权重表 | 校验引用完整、概率/数量合法；记录版本，不在查询中调用随机 |
| 羁绊VIP | 已有角色VIP字段及匹配的goddessvip行 | 服务端模块确认等级有效；动态上限与三资源加成必须用同一次读取的等级 |
| 神职 | 权威神职等级及所有已解锁IDLE_AWARD条目 | 每条独立概率与逐奖励项向上取整；保留多条，不只取最高等级一条 |
| 世界等级 | 区服权威等级、生成时间/版本、本人等级及增益配置 | 保留来源；本人等级不满足门槛时可判为不适用，满足时不能以缺快照默认0 |
| 礼包 | 服务端已持有记录ID、配置ID、结束秒数、active等原始状态、各条bonus | 提供原始状态给已确认的规则，不能先用另一套到期判断滤掉记录；多个礼包独立取整 |
| 三类活动 | 每类记录期及开服条件、等级条件（仅旧链适用者）、轮次、奖励表和gain_chance | 016/034与044分别判定；配置和角色轮次对应。不把客户端表缺概率解释为0 |
| 随机源 | 服务器在本次新计算中提供 | 不来自客户端；保存最终结果与计数，重放回执不重新抽样。测试可注入确定性随机源 |

VIP最大时长可能达到18小时，而当前`IdleRules.roll`只接受配置基础上限21600秒。将来接入VIP时须明确调整合法输入上限及验证跨多个累计窗口，不能仅改变客户端计时条就宣称VIP收益恢复。

## 缺失与无加成必须分开

输入装配拟返回三类内部结果；本批不把这些名字登记为真实协议或错误码。

| 内部结果 | 示例 | 拟定处理 |
|---|---|---|
| 可用 | 模块提供权威VIP0、有效神职等级、完整礼包列表 | 正常计算；0是经验证的业务值，不是占位默认值 |
| 已确认不适用 | 活动服务确认不在记录期；本人等级未达世界加成门槛；礼包服务确认没有持有记录 | 对应来源贡献0，保留不适用原因，不要求读取不会用到的概率表 |
| 无法确定 | 模块未恢复、读取失败、活动已开启但缺gain_chance、适用时缺世界等级快照、配置引用损坏 | 完整领取计算不得继续，也不发基础部分再补发；保持起点、计数、资产和回执不变 |

因此“当前没有活动模块”不是“当前没有活动”，“字段默认0”也不是“这名角色经权威模块确认无权益”。只读主页仍可以展示已接通的基础速率，并保留基础收益说明；无需因完整领取未就绪而中断现有挂机演出。

读取持有记录或查询说明不得顺带清理礼包active、更新活动轮次或发奖。将来需要维护这些持久状态时，由其所属服务按明确事务边界处理；只读快照不能承担资产操作。

## 计算结果与事务边界

拟定纯计算输出包含：基础奖励、原始随机奖励、按活动分别记录的奖励、各条神职追加、各项VIP/世界/礼包追加、最终合并奖励、累计秒数和分类计数前后值，以及所用配置/权威输入的版本信息。

保留分项是为了复验和幂等审计，不要求新增玩家界面。尤其不能在神职计算前把活动、基础和随机同类项提前合并：旧代码逐原始奖励项向上取整，提前合并会改变奇数量的结果。其他加成只以基础资源为底数，各条独立截断，不连乘。

后续领取授权后的建议顺序：

1. 校验会话与请求内容，按当前新主线约定获取角色锁；先查该角色的持久回执。
2. 已有同内容回执直接重放冻结结果，并按统一状态链返回当前资产；不重新读取已变化或暂不可用的加成依赖，不再次抽奖。不同内容同请求标识拒绝。
3. 新请求检查挂机操作版本与合法时段，装配一次权威输入。角色依赖在角色事务中读取；世界等级/活动全局快照须由其模块提供可标识版本的一致读，不能在每种资源计算时重新拉取。
4. 仅在所有适用依赖可用时执行纯计算。配置错误、溢出或依赖无法确定则拒绝本次，不消耗起点、不提交部分奖励。
5. 同一数据库事务持久化最终奖励、起点、累计窗口/保底、操作版本和回执，通过现有`AssetSyncService`推进资产revision；回滚无推送，提交后统一通知。跨请求并发只允许一个消费同一累计状态。
6. 客户端依旧走WS＋Protobuf、Controller校验后提交唯一Model；不新增HTTP回退，不用演出图标或本地倒计时写资产。具体`.proto`必须在正式接入批次先改后生成，不能将本文草案当作已存在消息。

此流程是设计约束，并未创建新表、回执类或服务。也没有为尚未恢复模块添加空Manager或返回固定0的适配器。

## 分步恢复与验收

| 阶段 | 可以交付的内容 | 不代表完成的部分 |
|---|---|---|
| 当前 | 本契约、输入清单、已实现基础随机的10项测试 | 完整加成与领取事务仍未实现 |
| 纯计算 | 对已核实的独立加成公式实现无状态计算及取整回归；保留原始分项，不依赖网络/数据库 | 没有权威输入链时不得接到领取按钮，不伪造权益 |
| 权威接入 | 按负责人确认范围分别恢复VIP、神职、世界、礼包和活动输入；缺失状态可辨识 | 单一模块就绪不等于所有完整领取前置就绪 |
| 新主线事务 | 授权后接通协议、持久回执、计数及统一状态；独立库验证并发、重放、断线、回滚 | 不复用旧IdleService测试或历史通过记录冒充本批验收 |
| 界面开放 | 前置齐全并明确授权后，再接领取及真实返回流程 | 不由按钮表现完成反推业务已开放 |

需要覆盖的新验收场景：权威VIP0与不可用区别、VIP时长跨窗、已确认未开启活动可跳过概率读取、活动开启缺概率整体拒绝、世界等级门槛两侧、多个礼包独立取整、神职多条与原始分项舍入、计算中依赖版本一致、历史回执在权益变化后固定、回滚及重复提交不改计数。

三项旧依据缺口继续见[规则记录](idle-reward-rules.md#不能默认补齐的依据缺口)。在涉及它们的实现前向负责人确认，不在本文选定活动概率缺省值、改礼包到期语义或擅自连接世界等级模块。宝箱领取、快速战斗、升级、穿脱仍关闭，清心/护盾待审不变。
