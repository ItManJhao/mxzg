# mxzg 多端产品需求

当前产品基线为中国大陆简体中文版，目标终端为 H5、App 和微信小游戏。三个终端共用玩法和角色数据，账号、支付、缓存与生命周期由平台适配层处理。Android、iOS 渠道及首发先后仍待确定。

2026-11-25 提出海外发行的可能性。首发地区、语种和渠道尚待负责人决定，现阶段可先在聊天和黑市验证多语言的成本与效果。[多语言评估与试点](localization-plan.md) · [项目总计划](restructuring-plan.md) · [已开放功能](development-progress.md)

## 重做原因与 1:1 还原标准

旧项目技术版本老、代码难以人工维护，因此更新技术底座和内部结构；不是重新设计游戏。**旧项目的玩法、内容、规则、数值、界面、交互与表现均以 1:1 还原为最终目标。** 现有实现不是反向定义产品的依据，阶段性简化必须进入差异清单并补齐。

内容和规则主要依据 mxzg 旧客户端、服务端和策划配置。效果与交互验收使用[正式服测试入口](https://meltia-jp-staging.funsgamex.com/perf-9003/)对照。G:/游爱/trunk 只参考写法和阅读习惯，具体见[开发约定](development-conventions.md)。

1:1 验收按对应账号状态、功能开放条件、配置版本、视口和动画阶段对照，覆盖正常操作及失败反馈；不能只做到“类似的页面”或“能升一级”。随机玩法核对规则、概率、保底与收据，不伪造相同随机结果。已确认简体中文/渠道/平台适配差异单独记录，任何其他玩家可见改动不因技术更新自动获得授权。

当源代码、策划表和正式服发生冲突，记录版本、输入、截图/回包及冲突点，向用户确认采用哪一版本；不默认某一份旧表必然等于正式服，不自行简化以绕过缺失证据。

## 最终范围与独立新版边界

2026-11-02 用户明确确认：**完整重做旧游戏，分批恢复玩法与社交；独立新版，暂不要求兼容旧客户端或迁移旧玩家。** 这不是只做首个可玩闭环。聊天、公会、活动及跨服等原游戏能力进入恢复清单；可以后置，但不能未经用户确认改为可选或删除。规则、数值和交互以原项目/策划与正式服对照为准，渠道、本地化和技术差异明确记录。

现有预制体的保留数量不定义最终功能范围；此前移除的计划外资产需要时从原仓库重新提取，不能因已清理资产而删减玩法。旧协议号、旧数据库表和旧客户端二进制兼容不作为约束；当前测试数据继续保留，不因独立新版而清库。

最终恢复范围与首个闭环分别验收。功能清单需覆盖旧服玩法模块和客户端入口，并标注未核实、规则核对、实现中、验证完成；只有数量或目录不能代替逐项完成证据。

## 当前批次的范围与开发顺序

七个底栏和主城基础入口已分批接通。当前先补聊天、黑市，再扩展副本大厅与公会玩法。各玩法的依赖、开发顺序与交付条件统一见[项目总计划](restructuring-plan.md)。

### 玩法与画面验收

- 从真实入口操作，在独立测试服检查读写、扣费、发奖和重登。挂机的收益周期、随机掉落、可信开服时间与资产回执已有独立说明。[挂机规则](idle-reward-rules.md) · [领取与结算](main-chapter-idle-settlement.md)
- 用正式服相同页签、开放条件、视口和动画时刻对照布局与交互。测试会话需要邀请时记录可用的截图及对照边界。日常以 Creator 预览为主，发布包按负责人要求单独构建。
- 界面布局与列表在 Creator 的 Prefab 中维护，滚动业务列表统一使用 SuperScroll 和 SuperContent。人工编辑体验由实际修改、保存和预览确认。[列表编排](super-scroll-authoring.md)
- 每次新增联网玩法先定规则与 Protobuf 契约，再生成类型、绑定 Prefab、接通 Controller 和 Model，并验证断线恢复。游戏业务统一走 WebSocket。资产由服务端事务提交，三端共享同一份业务语义。[通信契约](network-contract.md) · [架构](architecture.md)

## 重做版的设计原则

- 人能阅读、在编辑器修改 UI、追踪业务和独立排错是首要标准。客户端采用按功能组织的轻量 MVC，UIManager 统一界面生命周期；后端采用新的 Java/Spring Boot 模块化单体底座，按需验证并提取旧规则。具体职责、维护入口与后端取舍见 [架构与维护指南](architecture.md)。
- 根据当前三端能力、长期维护成本、工具链和团队可控性选择技术。现有 Creator/TypeScript 是待验证的候选基础，3.8.8 是当前版本事实，不是永久技术约束；更换或升级需要样包证据。
- 指定核心流程包括加载与登录、选区选服、主城、英雄、背包、挂机、出阵、主线战斗、结算与返回挂机。其构图、控件比例、切换反馈和规则以正式服为对照；简体中文、平台适配和必要技术差异单列说明。不得用“现代化”擅自替换核心布局、跳过步骤或改变玩法规则；开发联调壳、占位值和缺失功能不能当作最终方案。
- 未列入首测的旧系统仍进入完整恢复清单，按依赖分期；延期不等于删减。任何玩法简化、数值变化或不恢复决定都需用户明确确认。
- 新客户端按功能组织，明确数据所有权、业务服务和平台边界；优先简单可维护的实现，不为“现代化”堆叠框架、全局事件或分布式系统。
- 服务端、接口和配置重新评估。旧 Java 业务可复用、封装或替换；旧协议只在需要兼容时通过边界适配，新业务接口使用明确、版本化、可生成类型的契约。
- 现有迁移成果逐项评估：质量与新需求一致的保留，边界清晰的改造，过时壳层与重复路径替换或删除。重做不以清空仓库为起点，也不以修好全部旧实现为前置条件。

历史代码和迁移脚本不约束新工程架构；指定核心流程的正式服对照目标仍然有效。差异应区分已确认的本地化/平台差异、暂未实现的缺口和待用户确认的设计变更，不把技术现状自动解释成已确认需求。

## 核心玩家需求

### 账号与角色

- 平台凭据经服务端验证后换取游戏会话。手输数字 uid、客户端派生 uid 和本机 GM 只用于开发。
- 明确统一账号、渠道身份与区服角色的映射。同一账号在允许互通的终端上读取同一角色；微信与 App/H5 的账号绑定规则在接 SDK 前确定，不能默认自动互通。
- 支持公告、选服、创角、登录、断线重连、切换账号，以及前后台恢复后的重新同步。
- 维护、超时、鉴权失败、版本不兼容有明确状态和恢复路径，不能进入旧角色或伪造新手数据。

### 首个可玩的主循环

1. 新账号登录、创角、进入主城。
2. 获得英雄、查看技能、确认出阵，并由服务端保存。
3. 挑战当前主线、播放战报、结算，刷新角色、关卡和背包。
4. 挂机累积收益并领取，重登结果仍与服务端一致。
5. 使用基础道具、升级英雄，消耗和收益以服务端回包为准。
6. 退出、重登或换终端后，阵容、英雄、物品和关卡保持一致。

主城、英雄、背包、主线/挂机、基础召唤、基础养成、基础邮件组成首个功能闭环。聊天、公会、活动、跨服和高级养成分批恢复，属于最终范围；未完成期间入口明确未开放，不能把隐藏入口当作功能完成。

### 商业发行能力

可玩的测试版本与可收费发行版本分别验收。收费发行还需：

- 渠道登录、有效会话校验、明确的人民币商品目录和价格来源。
- 服务端创建订单、验证渠道支付、幂等发货、查询和补单。客户端支付回调不能直接发货。
- 公告、邮件、维护、开服、运营配置、封禁与可追溯操作记录。
- 客户端、协议和资源版本兼容策略，更新失败的恢复与回滚。
- 登录失败、支付失败、卡加载和战斗异常的日志与监控。

## 三端共同工程要求

- 业务通过统一接口调用登录、支付、存储、网络、生命周期、设备与安全区能力。
- development、staging、production 独立配置网关、资源地址、渠道与调试能力。线上连接不能依赖浏览器 URL 参数。
- 服务端是角色、物品、货币、阵容和关卡的最终事实来源。未同步、空列表、零值和失败分别表达。
- GM、协议探针、Mock 和回放与玩家入口分离。生产构建与服务端均限制调试能力，不能只隐藏按钮。
- 使用当前 Creator 候选方案时，Prefab 管结构与布局，View 管绑定与展示，模块 Controller 管请求/回包和业务协调，Model 管唯一状态，功能 API 管传输契约；UIManager 统一打开、取消、返回与销毁。职责边界不依赖最终引擎选择。
- 中文文案、图中文字、策划配置、公告和价格采用大陆基线。日服覆盖层只作参考，不能整套复制商品和渠道行为。

## 联网与社交基础要求

- 建立角色在线会话、稳定错误码、版本化请求/响应/推送契约，前后端类型与校验来自同一契约；新增消息从同一 Protobuf 定义生成，并检查前后端互通。
- 主动通知覆盖聊天、公会变更、邮件/红点、维护和顶号；离线后的快照/历史补拉与在线推送配套，不承诺只建长连接即可不丢消息。
- 资产请求使用独立的业务幂等键；传输请求序号只关联回包。提交后断线必须能确认原操作结果，不能盲目重发新操作。
- 推送与请求回包更新同一模块 Model；角色/区服会话代次与服务端版本防止旧消息覆盖新状态。
- 公会涉及多个玩家及共享实体，必须定义成员权限、锁/版本及一致性；不能只复用单角色行锁便宣称并发安全。
- 聊天频道、私聊/黑名单、历史/未读、频率和禁言按旧规则核对；聊天保存期、发布容量及跨服运行规模在相应实施阶段确认，不自行设定产品删减。

## H5 要求

- HTTPS 页面、可配置的安全网络入口，覆盖手机浏览器及微信内浏览器的触摸、音频启动与前后台恢复。
- 版本化资源和缓存失效策略，发布切换不能混用两版配置或脚本。
- 旧 PowerShell WebSocket 桥已退役，不恢复为生产基础。新通信入口需覆盖 WSS、连接鉴权、心跳、顶号、断线恢复和状态同步；是否独立部署网关以容量与故障隔离证据决定。
- 发布构建验证浏览器兼容性、窄屏安全区、横竖屏策略与断网恢复。

## App 要求

- Android/iOS 共用游戏核心，原生 SDK 通过适配层提供登录、支付和设备能力。
- 分别维护包标识、签名、渠道、版本和构建环境；iOS 在具备 Apple 工具链的环境构建与验证。
- 商店升级、原生包更新与资源更新各有策略，下载进度条不等于已安装热更新。
- 验证返回键、暂停/恢复、失焦、权限和网络变化；使用引擎/平台存储，不能假定浏览器全局对象存在。

## 微信小游戏要求

- 使用选定引擎的微信小游戏目标构建，在微信开发者工具和真机运行；当前工程采用 Creator 3.8.8。
- 适配微信身份、网络、存储、生命周期及所需支付；引擎已有适配和自建薄适配均以实包验证为准。
- 明确首包、启动场景、分包、远程资源、缓存与过期资源清理，按当前平台要求验收。
- 不依赖远程可执行脚本，不能照搬日服 WASM 网页的覆盖脚本与更新办法。

Creator 支持小游戏和原生发布，仍须配置各平台工程与能力。参考官方[微信小游戏发布](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/publish-wechatgame.html)、[原生平台发布](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/native-options.html)和 [Asset Bundle](https://docs.cocos.com/creator/3.8/manual/zh/asset/bundle.html)。具体包体限制和发行要求在提审前重新核对。

## 完成标准

功能从“资产存在”依次经过“界面绑定、真实读取、真实写入、服务端持久化、异常恢复、三端验证”。只读或 Mock 不能标为完整功能。

核心操作记录对应请求、回包、状态更新与重登结果；扣费和奖励增加重复点击、超时重试和失败检查。指定核心流程按正式服的视觉、交互和规则对照验收，记录视口、页签、动画时刻及账号数据差异；无法同账号时不伪造等级、英雄或战力来凑图。必要差异逐项说明，不能据单张截图或类型检查宣称已达到 1:1。

性能记录首屏可交互耗时、首屏下载量、峰值内存、战斗帧率和反复切页的内存趋势。先确定低端设备与网络条件，测量后制定数值门槛。源资源大小不等于包体、首屏下载量或内存占用。

## 尚需落定的发行决策

- App 是否同时首发 Android/iOS，以及商店和渠道 SDK。
- 海外首发地区、支持语种与渠道，以及目标地区的容量验收指标。游戏业务编码沿用 WS＋Protobuf。
- 三端账号互通、绑定和区服规则。
- 首测覆盖的具体副本与更多主城入口、商品与支付方案、发行接入负责人。

这些决策不阻塞边界整理和多端最小样包；正式账号与支付接入前必须落定。
