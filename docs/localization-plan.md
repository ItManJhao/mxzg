# 海外版多语言评估与试点

**建议先做一段能玩的双语流程。** 从正在规划的聊天、黑市入手，让两名使用不同界面语言的角色在同服聊天，再让同一角色切换语言、看同一件商品并完成购买。这一段同时覆盖输入法、长文本、系统提示、道具名、价格、数量和扣费反馈。建议首轮使用简体中文和英语，英语可检验长按钮和复数；日语可借正式服画面及旧译核对专名。试点语种可随目标市场调整。

截至 2026-11-25，海外首发地区、渠道和语种尚待负责人决定。当前基线仍为简中。共用一套玩法与服务端数据，按语言加载文字、字体和必要的带字美术，是现有工程改动最小的路径。[项目总计划](restructuring-plan.md) · [产品需求](product-requirements.md)

## 开发需要具备什么

1. **语言选择与回退。** 首次按已支持的设备语言选择，玩家手动选择后在下次启动沿用。用标准语言标签标识资源，例如 `zh-Hans`、`en`、`ja`，并显式映射旧资源名。建议首批切换时回到加载页重新装载，避免同一窗口混用新旧文本和字体。下载失败时使用已校验的同版缓存或内置基线，向玩家显示当前语言。语言包缺键在开发检查中列出。[W3C 语言标签说明](https://www.w3.org/International/articles/language-tags/)
2. **翻译输入与展示。** 沿用物品、英雄、技能等现有语言键。为新增按钮、错误码、系统广播建立稳定键、语境和截图；校验旧模板的 `[1]` 等参数、富文本标记、换行及顺序。数量和时间使用完整句子模板，允许译者重排参数和选择复数形式。金额、数字缩写、时间格式由展示层选择。服务端按既有区服规则决定扣费、开服日、限购和上海时间重置，切语言不能切换这些规则。[配置管线](config-pipeline.md) · [Unicode 复数规则](https://cldr.unicode.org/index/cldr-spec/plural-rules)
3. **字体、布局与图片。** 对每种候选语种核实字体授权与实际字形，分别测 UI 字体、数字位图字体和系统输入框。优先把可编辑文字从带字底图移到现有 Prefab 的 Label；无法分离的徽标或横幅按语言提供 SpriteFrame，保留原布局与资源标识。窄屏实测换行、按钮、道具数量、滚动列表和多条飘字。若首发选从右至左的语言，另排镜像、双向混排和输入验收。
4. **聊天与历史数据。** 用户发言按原文存取。频道名、禁言或限频反馈、系统消息外壳用接收者的界面语言显示。用不同语种的两台客户端验证输入法合成、表情、长度边界、拉黑、重连历史与未读。系统模板参数按类型转义，保留昵称原貌。切语言前后核对消息编号、角色、库存与回执。
5. **发行与运营。** 确定首发地区后再定 App 商店、H5 或其他渠道的登录与支付、当地商店价格和币种、客服、聊天审核、隐私与年龄提示、翻译和字体授权的负责人。语言、发行地区、游戏区服分别配置。跨地区延迟、字体及语音包体、活动时刻、更新与回滚需在目标设备验证。涉及地区政策和渠道准入的细则在选定市场后专项核实。

## 怎样推进和决定投入

| 阶段 | 实际交付 | 验收依据 |
|---|---|---|
| 聊天开发时 | 策划列出本服频道、系统提示与错误码；客户端接通首屏语言选择、两种语言的文本和字体；服务端保留玩家原文 | 两个不同界面语言的账号世界发言、私聊、退出重登。双方看到相同的发言原文，各自看到对应的系统提示；窄屏能完整阅读长句 |
| 黑市开发时 | 复用同一商品 ID、价格与规则，只切换名称、说明、按钮和结果提示；验证现有共用购买窗 | 同一报价切换语言仍有效。实际购买、余额不足、跨刷新期和原请求重试均得到正确提示，余额、库存与限购和语言无关 |
| 试点复盘 | 策划汇总可复用旧译、缺键、占位符差异；美术列出需重制的图片和字体；开发记录首屏大小、首次加载与切换耗时；母语审校人员签收截图 | 试点关键流程缺译、错参、缺字与挡住操作的裁切全部清零。按实测每页修订工时、待审字符数和图片张数估算每个候选语种，供负责人选市场、语种和投入 |
| 确认发行后 | 先扩登录、主城、好友邮件与商店，再扩战斗、副本、公会、活动及运营工具；同一内容版本带各语种的翻译差异清单 | 目标渠道实机走完新号首日流程、系统邮件领奖、弱网重连与语言包版本回滚。逐语种记录画面、性能、审核和客服就绪情况 |

第一项可执行工作是从聊天浮标到首次成功发言，把页面实际用到的文案键、系统提示、玩家输入和两张语言截图放在同一份验收记录里。完成这一段即可判断导出、显示和输入的改造成本；黑市试点再补交易与带字美术的成本。
